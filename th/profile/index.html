01 / เส้นแรกของความฝัน

ก่อนเส้นทาง AI / วันที่เริ่มอยากออกแบบ

ก่อนจะเขียนโค้ด
ผมอยากวาดบ้าน

ตอนเด็ก ผมอยากเป็นสถาปนิก อยากออกแบบพื้นที่ที่คนได้เข้าไปใช้ชีวิตอยู่จริง

  1. 01นึกถึงบ้านสักหลัง
  2. 02ลากเส้นแรกลงไป
  3. 03เปลี่ยนเส้นวาดเป็นโค้ด

พอโตขึ้น ผมเลือกเรียนวิศวกรรมซอฟต์แวร์ ความตั้งใจเรื่องการออกแบบยังอยู่เหมือนเดิม เพียงแต่สิ่งที่อยู่ตรงหน้าเปลี่ยนจากกระดาษเขียนแบบมาเป็นหน้าจอ

ผมเจอพื้นที่ของตัวเองในงาน Frontend ตรงที่โค้ดเริ่มมีรูปร่าง และคนใช้งานเริ่มโต้ตอบกับสิ่งที่ผมสร้างได้จริง ผมชอบคิดเผื่อรายละเอียดเล็ก ๆ ตั้งแต่เขาจะมองตรงไหนก่อน กดอะไรต่อ ไปจนถึงความรู้สึกระหว่างใช้งาน

ความฝันเรื่องสถาปัตยกรรมงานฝีมือสาย Frontend
พอสิ่งที่ออกแบบต้องถูกนำไปใช้จริง แค่ดูดีอย่างเดียวไม่พอ แต่ต้องพึ่งพาได้ด้วยถ้ามีคนต้องพึ่งพาสิ่งที่ผมสร้าง งานนั้นต้องไว้ใจได้แค่ไหน?↓

02 / รากฐานของงาน

ก่อนเริ่มพัฒนา AI / พื้นฐาน Frontend

เมื่อสิ่งที่สร้าง
มีคนต้องใช้จริง

หน้าจอแต่ละส่วนไม่ได้อยู่ลำพัง แต่เป็นชิ้นส่วนหนึ่งของระบบใหญ่ที่คนใช้งานอยู่ทุกวัน

  1. 01สร้างชิ้นส่วนแรก
  2. 02ประกอบเข้ากับระบบ
  3. 03ตรวจให้แน่ใจก่อนส่งต่อ

ที่ Allianz Technology ผมได้ทำ Frontend ในระบบองค์กร งานหนึ่งหน้าจอเป็นส่วนหนึ่งของระบบที่ใหญ่กว่าเสมอ สิ่งที่ดูเรียบร้อยบนเครื่องของผม ยังต้องทำงานร่วมกับส่วนอื่นและรองรับการใช้งานจริงได้

การทำงานร่วมกับทีมในมิวนิกและกรุงเทพฯ ทำให้ผมมองงานออกแบบกว้างขึ้น จุดเล็ก ๆ ที่ผู้ใช้อาจไม่ทันสังเกต กลับเป็นสิ่งที่คนทำต้องใส่ใจให้มากพอ

Allianz Technologyพัฒนา Angular และ frontend ของระบบองค์กร พร้อมประสานงานกับผู้เกี่ยวข้องและทีมวิศวกรรมในมิวนิกและกรุงเทพฯ

Angularระบบองค์กรมิวนิก ↔ กรุงเทพฯ

  1. 01ฟังให้เข้าใจโจทย์
  2. 02เชื่อมงานข้ามทีม
  3. 03ประกอบทุกส่วนเข้าด้วยกัน

งานระบบธนาคารองค์กรที่ Accenture เริ่มจากการฟังให้เข้าใจว่าผู้เกี่ยวข้องต้องการอะไร แล้วแปลงสิ่งนั้นเป็นงาน Frontend ที่ทีมจะพัฒนาและส่งมอบร่วมกัน

เมื่อวิศวกรทำงานกันคนละสถานที่ การสื่อสารให้เข้าใจตรงกันสำคัญไม่แพ้การเขียนโค้ด ผมได้ฝึกมองภาพรวมให้เห็นว่า ส่วนที่ผมรับผิดชอบจะไปเชื่อมต่อกับงานของคนอื่นอย่างไร

Accentureพัฒนา frontend สำหรับงานธนาคารองค์กร แปลงความต้องการของผู้เกี่ยวข้องและทำงานร่วมกับทีมวิศวกรรมที่อยู่ต่างสถานที่

ระบบธนาคารองค์กรทำความเข้าใจโจทย์ทำงานข้ามทีม
ต่อมา ในปี 2567 ขณะที่ยังทำงานอยู่ ttb ผมเริ่มพัฒนาความสามารถด้าน AIถ้า AI เข้ามาช่วยในงานที่ผมทำอยู่ทุกวัน จะเกิดอะไรขึ้น?↓

04 / วันที่ความเป็นไปได้เริ่มมีความหมาย

2567 / 2024เริ่มพัฒนา AI ขณะยังทำงานอยู่ ttb

ผมเห็นความเป็นไปได้

ตอนนั้น ผมเริ่มพัฒนาความสามารถด้าน AI ขณะที่ยังทำงานอยู่ ttb ความเชื่อของผมยังต้องพิสูจน์ด้วยงานที่ทำ

  1. 01เห็นสิ่งที่อยากสร้าง
  2. 02พิสูจน์ด้วยงานที่ตรวจได้
  3. 03ลงมือให้คนอื่นลองได้

คนรอบตัวบางคนยังไม่เชื่อในสิ่งที่ผมเห็น แม้แต่บางคนที่ทำงานสายเดียวกัน ผมรู้ดีว่าลำพังความเชื่อคงพาเรื่องนี้ไปได้ไม่ไกล ผมจึงอยากสร้างบางอย่างที่เขาลองจับต้องและใช้งานได้จริง

ผมเริ่มจากงานตรงหน้า นำ GPT เข้ามาช่วยในขั้นตอนงานที่เกี่ยวกับ Jira, Confluence และ Bitbucket โดยยังให้คนเป็นผู้ตรวจทานก่อนนำผลลัพธ์ไปใช้ ความเป็นไปได้ที่เคยคิดไว้เริ่มกลายเป็นโจทย์จริงให้ลงมือแก้

คำตอบจากโมเดลเป็นเพียงจุดเริ่มต้น ผมยังต้องดูว่าข้อมูลนั้นมาจากไหน ขาดอะไรไป และควรหยุดให้คนตรวจตรงจุดไหน ยิ่งลงมือทำ ผมยิ่งเห็นระยะห่างระหว่างคำตอบที่ได้จาก AI กับเครื่องมือที่คนจะวางใจหยิบมาใช้จริง

ttb sparkงานวิศวกรรมซอฟต์แวร์อาวุโสในธุรกิจธนาคารและ Frontend เริ่มพัฒนาความสามารถด้าน AI ในปี 2567 ขณะยังอยู่ ttb รวมถึงขั้นตอนงานที่ใช้ GPT ช่วยงาน Jira, Confluence และ Bitbucket โดยมีคนตรวจทาน

ผมอยากให้เขาได้ลอง ก่อนจะขอให้เขาเชื่อ
Jira · Confluence · Bitbucketคนยังเป็นผู้ตรวจทาน

05 / อีกด้านของการเริ่มต้น

เบื้องหลังเส้นทาง AI ที่เริ่มขณะอยู่ ttb

บางคนยังไม่เชื่อ
ผมยังลงมือลอง

ระหว่างที่ผมเริ่มเรียนรู้และพัฒนา AI คนรอบตัวบางคนยังมองไม่เห็นสิ่งเดียวกัน

  1. 01ประคองสิ่งที่ยังเชื่อ
  2. 02เจอสิ่งที่ยังไปต่อไม่ได้
  3. 03อยู่กับคำถามสักพัก
  4. 04กลับไปดูว่าพลาดตรงไหน
  5. 05ยังกลับมาทำต่อ

บางคนทำงานสายเดียวกันกับผมด้วยซ้ำ ผมเข้าใจดีว่าความเชื่อของผมยังเป็นเพียงคำพูด ตราบใดที่ยังไม่มีอะไรให้เขาลองใช้จริง ช่วงแรกผมจึงเริ่มลงมือด้วยตัวเอง ค่อย ๆ สร้างสิ่งที่อยากเห็นขึ้นมาทีละส่วน

พอลงมือจริง ปัญหาก็ทยอยเข้ามาทีละอย่าง บางเรื่องต้องรื้อวิธีคิดใหม่ บางเรื่องต้องกลับไปค้นคว้าเพิ่ม ทุกสกิลและ Workflow ที่ผมสร้างล้วนเกิดจากปัญหาที่ผมเจอมากับตัวและพยายามทำความเข้าใจมัน

ผมกลับมาทำต่อทุกสัปดาห์ ลอง แก้ แล้วทบทวนใหม่ สิ่งที่ค่อย ๆ ก่อตัวขึ้นจากความต่อเนื่องนั้น คือ HolyMind

ผมยังไม่มีทุกคำตอบ แต่ยังอยากกลับไปทำให้มันดีขึ้นอีก
เริ่มลงมือด้วยตัวเองกลับมาพัฒนาทุกสัปดาห์
ปัญหาที่เจอระหว่างทางค่อย ๆ กลายเป็นสิ่งที่ผมเก็บไว้ใช้ในงานครั้งถัดไปจะเก็บบทเรียนที่เจอ ให้กลายเป็นเครื่องมือที่ช่วยงานครั้งต่อไปได้อย่างไร?↓

06 / บทเรียนที่เริ่มมีตัวตน

ผมปล่อยให้สิ่งที่เจอระหว่างพัฒนา AI ตกตะกอนก่อน แล้วค่อยถามว่า อะไรในนั้นควรเก็บไว้

  1. 01เก็บสิ่งที่ปัญหาสอน
  2. 02ออกไปเรียนรู้วิธีอื่น
  3. 03ประกอบเป็นสกิลของตัวเอง
  4. 04ขัดเกลาจนมีจุดเด่น

จากนั้นผมมองออกไปนอกกรอบที่ตัวเองคุ้นเคย ค้นคว้าแนวคิด งานวิจัย และเครื่องมือจากคนที่ทำเรื่องนั้นได้ดี คัดเลือกสิ่งที่ดีที่สุดเท่าที่หาได้จากทั่วโลก มาทดลองกับปัญหาที่ผมเคยเจอจริง

ผมคัด ทดลอง และปรับแก้จนแต่ละสกิลเริ่มมีหน้าที่ มีวิธีทำงาน และมีตัวตนของตัวเอง พอนำมาเชื่อมต่อเป็น Workflow บทเรียนจากงานหนึ่งก็ช่วยให้อีกงานตั้งต้นได้ดีขึ้น

สำหรับผม MOAT ของสกิลอยู่ตรงนี้ อยู่ที่การเลือกว่าควรประกอบอะไรเข้าด้วยกัน อะไรควรตัดออก และรายละเอียดที่ขัดเกลาซ้ำมาหลายรอบ ผมอยากให้แต่ละสกิลพิสูจน์คุณค่าด้วยงานที่มันทำได้จริง

  1. เจอปัญหา
  2. ทบทวน
  3. ค้นคว้า
  4. ประกอบความรู้
  5. ลองใช้และปรับ

ฉากเล่าเรื่องผ่านสัญลักษณ์ ไม่ได้จำลองเหตุการณ์จริง

07 / สิ่งที่ผมอยากให้คนรู้สึก

ผมอยากให้คนรู้สึกว่า “อยากใช้” ตั้งแต่ก่อนจะรู้ว่าข้างหลังมันยากแค่ไหน

  1. 01มองให้ถึงสิ่งที่ซ่อนอยู่
  2. 02ออกแบบทางเข้าให้เข้าใจง่าย
  3. 03ให้เขาเป็นคนเลือก
  4. 04ชวนให้อยากกลับมาใช้

เมื่อมาถึงยุค AI ความชอบในงาน Frontend กับพื้นฐานวิศวกรรมซอฟต์แวร์ของผมทำงานร่วมกันได้เต็มที่ขึ้น ผมออกแบบได้ทั้งกลไกการทำงานข้างหลัง และประสบการณ์ของคนที่เข้ามาใช้งานจริง

ผมอยากให้หน้าจอช่วยให้เขาเริ่มต้นได้ง่าย รู้ว่าตอนนี้ระบบกำลังทำอะไร และเห็นชัดว่าขั้นต่อไปเลือกอะไรได้บ้าง ภาระความซับซ้อนข้างหลังเป็นหน้าที่ที่ผมต้องจัดการให้เรียบร้อย ส่วนเหตุผล ที่มาของข้อมูล และจุดที่ต้องให้คนตรวจทาน ต้องยังเปิดดูได้เสมอเมื่อต้องการ

หน้าตาที่ดีช่วยชวนให้คนอยากเปิดเข้ามา แต่ความใส่ใจในทุกจังหวะการใช้งานต่างหากที่ทำให้เขาอยากหยิบเครื่องมือนั้นกลับมาใช้ทำงานอีก นี่คือความหมายของคำว่า AI experiences สำหรับผม

Independent AI Solutions Architectออกแบบและพัฒนาเครื่องมือที่ใช้ AI ช่วยงาน ด้วย React, FastAPI และ PostgreSQL ตั้งแต่ทำความเข้าใจโจทย์ วางสิทธิ์เข้าถึงข้อมูล ไปจนถึงการแสดงที่มาของคำตอบและจุดที่ต้องให้คนตรวจทาน

ตามสกิลไปดูในผลงาน

งานที่เปิดให้คนตรวจทานได้จากงานซ้ำ ๆ สู่คำตอบที่เห็นชัดว่าใครต้องตรวจต่อ

  1. โจทย์

    แม้จะเป็นงานที่ทำซ้ำ ก็ยังต้องมีคนรับผิดชอบและรู้ว่าต้องตรวจตรงไหน

  2. วิธีที่เลือก

    วางร่างคำตอบ ข้อมูลที่ยังขาด และเรื่องที่รอการตัดสินใจไว้ให้เห็นด้วยกัน

  3. ลองตามขั้นตอน

    เลือกตัวอย่างงานซ้ำ ๆ เปิดดูข้อมูลตั้งต้น แล้วอ่านร่างผลลัพธ์ก่อนส่งต่อ

  4. ลองดูในผลงาน

    ทดลองใช้บน Workbench อ่านขั้นตอนการทำงาน
คำตอบที่ตามกลับไปดูที่มาได้จากข้อมูลที่กระจัดกระจาย สู่คำตอบที่มีหลักฐานรองรับ

  1. โจทย์

    ถ้าไม่เห็นข้อมูลที่รองรับ คนใช้ก็ประเมินคำตอบที่ดูมั่นใจได้ยาก

  2. วิธีที่เลือก

    เชื่อมข้อความกับแหล่งข้อมูลที่อนุญาตให้ใช้ และเว้นส่วนที่ยังไม่มีหลักฐานไว้

  3. ลองตามขั้นตอน

    เลือกตัวอย่างข้อมูลกระจัดกระจาย แล้วตามข้อความในร่างกลับไปยังแหล่งอ้างอิงสมมติ

  4. ลองดูในผลงาน

    เปิดดูตัวอย่างบน Workbench อ่านเรื่องขอบเขตข้อมูล
ต่อยอดสิ่งที่เลือกไว้สู่ขั้นถัดไปจากสกิลที่สนใจ สู่โจทย์ที่เริ่มคุยงานต่อได้ทันที

  1. โจทย์

    พอเจอสกิลที่น่าสนใจ ผู้ชมควรนำสิ่งนั้นไปใช้ตั้งต้นคุยงานต่อได้

  2. วิธีที่เลือก

    เก็บโจทย์และสกิลที่ผู้ชมเลือกไว้ด้วยกัน ระหว่างสำรวจและเตรียมข้อมูลคุยงาน

  3. ลองตามขั้นตอน

    เลือกสถานการณ์ ลองดูสกิลของ HolyMind แล้วนำสกิลนั้นไปใส่ในแบบสรุปโจทย์

  4. ลองดูในผลงาน

    สำรวจคลังสกิล HolyMind ดูว่าสิ่งที่เลือกไปต่ออย่างไร
ทดลอง Workbench บนเว็บไซต์ อ่านแนวคิดและขั้นตอนการทำงาน ดูว่าสิ่งที่เลือกไปต่อเป็นโจทย์อย่างไร อ่านเรื่องภาพเคลื่อนไหวและเสียงที่เชื่อมกัน
โจทย์ตั้งต้นขั้นตอนทำงานผลลัพธ์ที่ตรวจดูได้
เบื้องหลังแนวคิดทั้งหมดนี้ มาจากงานจริงที่ผมสะสมมาตลอดหลายปีดูประสบการณ์และงานที่ผมรับผิดชอบ↓
